Runtime check method for the statuses (use it; the issue's "Done when" asks for a runtime check of each duration).

Method: give the player the move that causes the status, then use it on a wild monster through the game's own code path. Only the move choice is forced.
1. Write one new script, verification/v7-trace/status_probe.py, built on the existing harness (retail_trace.py, drive.py, boot_to_dungeon.txt, scripted turn inputs; see docs/verification.md for how the other probes are documented). Its files must be on the planner's Files list, together with the docs/verification.md entry for it.
2. After the first dungeon floor is reached, write the player's (team[0]) move slots at info+0xF4: 4 entries of 6 bytes, flags at +0, move id (u16) at +2, PP at +4 (docs/re/structs.md, "moves"; confirm the layout there before you write anything). Put the move id whose effect causes the status under test in a slot. Move ids and effects are in docs/re/move-effects.md. Label this poke FORCED in the probe's output and in the notes, as msg_lcg_probe.py does.
3. Replay scripted inputs that use that move on an adjacent wild monster (combat_inputs.txt shows how the player attacks), then read the target's status bytes (offsets in docs/re/status.md) at every turn until the status ends. Record the start value, the number of turns until the end, and the SHA-256 of the trace.
4. The run must repeat: the same trace hash across two runs. A move can miss and a target can be immune (type or ability). If the status did not land, change the inputs or the move target; do not claim a duration you did not observe. A status you could not observe stays [hypothesis] with the reason.
5. Tag a duration [blue-verified] runtime only when the probe observed it. Record only the hash and the command in docs; write all probe output to the scratch directory, outside the repo. Run probes with ~/venvs/desmume/bin/python -I, SDL_VIDEODRIVER=dummy, XDG_CONFIG_HOME in the scratch directory and a throwaway ROM file name.
